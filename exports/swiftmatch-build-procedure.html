PHASE 01

Project & Monorepo Foundation

Goal: A clean, type-safe multi-package workspace where each app and library manages its own dependencies.

Steps

  1. Initialize a pnpm workspace monorepo with pnpm-workspace.yaml declaring the artifacts/* and lib/* package globs.
  2. Create a shared tsconfig.base.json with strict TypeScript defaults (composite: true, incremental builds) and a root tsconfig.json solution file referencing all composite libraries.
  3. Pin shared dependency versions in the workspace catalog so every package resolves the same React, TypeScript, etc.
  4. Establish the folder structure: deployable apps in artifacts/, shared code in lib/, utility scripts in scripts/.
# Resulting structure
artifacts-monorepo/
├── artifacts/
│   ├── api-server/     # Express API
│   └── swiftmatch/     # React + Vite frontend
├── lib/
│   ├── api-spec/       # OpenAPI + Orval config
│   ├── api-client-react/  # Generated React Query hooks
│   ├── api-zod/        # Generated Zod schemas
│   └── db/             # Drizzle schema + connection
├── pnpm-workspace.yaml
└── tsconfig.base.json

Principle: Leaf apps (artifacts/*) never import each other. Anything shared becomes a lib/* package — keeping boundaries clean and types portable.

PHASE 02

Database Schema Design

Goal: A structured talent graph in PostgreSQL, modeled with Drizzle ORM in the @workspace/db library.

Steps

  1. Provision a PostgreSQL database; expose its connection via the DATABASE_URL environment variable.
  2. Model the domain as Drizzle schema files, one per concern, under lib/db/schema/.
  3. Use drizzle-zod to derive validation schemas directly from table definitions, keeping DB and API contracts in sync.
  4. Push schema changes with pnpm --filter @workspace/db run push (no manual SQL migrations).

Core Tables

applicants.tsCandidate profiles: personal info, contact, skills, history, references, preferences
assessments.tsAssessment definitions + assessment_results (with nullable job_id FK)
jobs.tsJob postings, custom_questions JSONB, and job_applications
courses.tsTraining / course recommendations (the skill-enhancement "bench")

PHASE 03

Contract-First API Spec

Goal: Define every endpoint once in OpenAPI, then generate type-safe clients and validators — no hand-written API glue.

Steps

  1. Author the OpenAPI specification in lib/api-spec/ describing all routes, request bodies, and responses.
  2. Configure Orval to generate, from that single spec:
    • @workspace/api-client-react — React Query hooks for the frontend.
    • @workspace/api-zod — Zod schemas for runtime validation on both sides.
  3. Run codegen whenever the contract changes:
pnpm --filter @workspace/api-spec run codegen

Why contract-first: The server validates inputs/outputs with the generated Zod schemas, and the client calls the generated hooks. The compiler catches any drift between frontend and backend before it ships.

Note: the OpenAPI info.title drives generated filenames, so it stays fixed once established.

PHASE 04

Backend API Server

Goal: An Express 5 + TypeScript server exposing the talent graph, with auto-seeded demo data.

Steps

  1. Scaffold the @workspace/api-server Express application; bind it to the PORT env var and mount everything under the /api base path.
  2. Implement route handlers grouped by concern (applicants, assessments, jobs, courses, skills, résumé, auth).
  3. Validate all inputs and outputs against the generated Zod schemas.
  4. Use structured logging (req.log in handlers) — never console.log in server code.
  5. Auto-seed demo content on boot: assessments, 6 sample jobs, 8 courses.

Key Endpoints

GET/POST /api/applicantsList / create candidate profiles
GET /api/jobs · /:idList / fetch postings (answer keys stripped)
POST /api/jobs/:id/applyApply to a job (JWT required, 409 if duplicate)

GET /api/skills/suggestions?q=Skill autocomplete
PHASE 05

Frontend Scaffold

Goal: A fast, polished React single-page app served at the root path.

Steps

  1. Scaffold the @workspace/swiftmatch app with React + Vite.
  2. Add Tailwind CSS and shadcn/ui for a consistent design system; Framer Motion for animation.
  3. Configure Vite to read PORT and allow proxied hosts (server.allowedHosts: true) so the preview renders through Replit's iframe proxy.
  4. Wire data fetching through the generated @workspace/api-client-react hooks — using base-path-aware URLs, never root-relative ones.
  5. Establish the brand: navy primary, orange accent, the "Don't search. Get spotted." identity.

Routing model: A global reverse proxy routes by path — the frontend lives at /, the API at /api. Each service handles its own full base path; no Vite proxy hacks needed.

  3. Add the résumé upload card above the wizard (see Phase 07) to pre-fill the steps.
PHASE 07

Résumé Auto-Fill (AI)

Goal: Remove onboarding friction — let a candidate upload a résumé and have the profile fill itself.

Steps

  1. Add a résumé upload card (PDF, .docx/.doc, plain text; up to 10MB) above the 10-step wizard.
  2. Implement POST /api/resume/parse (multipart, field resume).
  3. Extract raw text server-side: pdf-parse for PDFs, mammoth for DOCX.
  4. Send the text to GPT (gpt-5-mini) via the Replit-managed OpenAI AI Integration — no user API key required.
  5. Map the model's structured output to wizard fields: name, contact, address, skills, employment history, certificates, salary, availability, social links.
# Managed via env vars — billed to Replit credits
AI_INTEGRATIONS_OPENAI_BASE_URL
AI_INTEGRATIONS_OPENAI_API_KEY

Result: A candidate goes from "upload" to a mostly-complete profile in seconds, then reviews and refines — dramatically improving completion rates.

PHASE 08

Assessment Engine

Goal: Score every candidate objectively across five dimensions and 22 industries — fairly and un-gameably.

The Five Dimensions

Knowledge & Expertise

Industry competency; difficulty-weighted, role-prioritized banks.

Personality & Work Style

DOPE Bird / MBTI routing by role & seniority.

Cultural Fit

Workplace-norm alignment, per industry.

Critical Thinking

Scenario-based reasoning.

AI Readiness

50-question industry-scoped bank measuring practical AI-tool fluency — the differentiator.

Steps

  1. Build the question banks in industry-questions.ts with INDUSTRY_QUESTIONS, INDUSTRY_ROLES, and an ANSWER_KEY per industry.
  2. Implement pickQuiz to randomize 10 questions per session (3 easy, 4 medium, 3 hard) so no two candidates get the same test.
  3. Grade server-side only — the client never sees answer keys.
  4. Enforce a 1-month retake cooldown (bypassed for the owner account during testing).
  5. Normalize raw industry strings to canonical quiz keys via normalizeIndustry().
  6. Scale coverage to 22 industries — including adding Virtual Assistance end-to-end (question bank, routing, role maps, slug maps).
PHASE 09

Jobs, Applications & Matching

Goal: Let candidates apply to jobs and auto-trigger the right assessment, while linking results back to each application.

Steps

  1. Render job cards and a detail panel with an Apply button (hidden for employer sessions).
  2. On apply: if JWT valid → POST /api/jobs/:id/apply → redirect to the assessment pre-loaded with the job's industry/role/company; if no JWT → redirect to signup.
  3. Create a job_applications row (unique per applicant+job; 409 on duplicates).
  4. On K&E submit, pass the jobId so the score updates job_applications.ke_score and sets status = "assessed".
  5. Show a job-context banner in the quiz and auto-start the assessment from URL params or from the profile's target industry/role.

Outcome: Applying and getting measured become a single, seamless flow — every application carries an objective score.

PHASE 10

Recruiter Custom Assessments

Goal: Let recruiters attach their own scored questions to a specific job and grade them automatically.

Steps

  1. Add a custom_questions JSONB column to jobs; each question = { id, prompt, type, options?, correctAnswers[] }.
  2. Build the recruiter question builder in the Jobs editor — multiple-choice (checkbox for correct option) and text (pipe-separated accepted answers). Use functional setState to avoid stale-closure drops on rapid edits.
  3. Gate editing with canEditJob = admin OR employer-owner.
  4. Strip answer keys from all public reads (stripJobAnswerKeys); expose sanitized questions via GET /api/jobs/:id/custom-assessment.
  5. Grade on submit (POST .../custom-assessment/submit): case-insensitive trimmed equality; persist atomically with INSERT … ON CONFLICT … DO UPDATE when a profile exists.

Security principle: Correct answers never leave the server for public consumers. The grading boundary lives entirely server-side.

PHASE 11

Employer Report & Decisioning

Goal: Give employers a ranked, comparable candidate pool and a way to act on it.

Steps

  1. Build the Candidate Analytics Report: a ranked pool scored across all five dimensions, with radar comparison (top candidate vs. pool average).
  2. Add a job-fit matching view ranking candidates by compatibility (industry, role, level, assessment factors).
  3. Render per-candidate Pass / Fail decision radios in both tables — emerald Pass, rose Fail — isolated from the row's "View Report" click.
  4. Hold decisions in a state map keyed by candidate id (UI-first), ready to wire to a backend column and notifications.

Planned Next (decisioning pipeline)

  • Persist decisions to a DB column via a new endpoint.
  • On Pass → email the candidate a hiring-process invite.
  • On Fail → respectful thank-you email plus training / alternative-industry suggestions.
PHASE 12

Authentication & Owner Accounts

Goal: Identify candidates vs. employers vs. admins, and enable safe testing bypasses.

Steps

  1. Implement signup/login issuing a JWT; protect apply, submit, and admin routes with it.
  2. Maintain owner/admin emails in two synced places: backend DEFAULT_OWNER_EMAILS (extendable via OWNER_EMAILS env var) and frontend owner.ts (isOwnerEmail()).
  3. Add owner bypasses for testing: skip email confirmation on signup, and treat owner accounts as premium.
  4. Tie bypasses to the authenticated identity (useAuth() + isOwnerEmail()), not device-local flags.

Deferred: Email delivery (confirmation + reset). The email lib logs the link to the server console until an SMTP/email integration is connected — a known, documented gap.

PHASE 13

Premium Gating

Goal: Monetize the full analytics report behind a premium tier.

Steps

  1. Compute premium status on the Results page: isPremium = localStorage.sm_subscription === "active" || isOwnerEmail(user?.email).
  2. Wrap the full report in a LockOverlay — blurred preview + subscribe upsell for free users.
  3. Owner accounts see the full report with no lock, for demos and testing.

Known limitation & next build: the gate is currently client-side (bypassable). Moving it server-side — so the API itself withholds premium data from unentitled users — is the priority hardening step before charging real customers.

PHASE 14

Supporting Artifacts & Launch

Goal: Surround the product with everything needed to demo, market, and ship it.

Steps

  1. Build a buildathon marketing site artifact (brand/positioning showcase) at its own path.
  2. Produce a 2-minute product walkthrough video artifact.
  3. Maintain a mockup-sandbox artifact for isolated component previews on the canvas.
  4. Verify each artifact with pnpm --filter @workspace/<slug> run typecheck (not build, which needs workflow env vars).
  5. Run each app via its workflow; confirm the preview renders through the proxy.
  6. Review major features with an architect pass; fix severe issues before shipping.
  7. Deploy — the platform handles build, hosting, TLS, and health checks.
